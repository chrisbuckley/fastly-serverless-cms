Building a CMS That Runs Entirely at the Edge

May 18, 2026 8 min read Chris Buckley
fastly edge compute architecture

Every CMS you have ever used follows the same basic pattern: a reader makes a request, it hits a CDN, the CDN checks its cache, and on a miss it reaches back to an origin server — some application running in a datacenter — that queries a database, renders a template, and sends HTML back through the chain. The CDN then caches that response for next time. It works. It has worked for twenty years. But what if you deleted the origin entirely?

That is the idea behind this project. Edge CMS is a fully functional content management system where every component — the application logic, the data store, the image pipeline, the caching layer — runs at the edge. No origin server. No centralized database. No cold starts from a container spinning up in us-east-1. A reader in Tokyo gets their response from a Fastly POP in Tokyo, built from data that already lives there.

Why the Edge Changes Everything

Traditional architectures treat the CDN as a dumb cache sitting in front of the real application. The edge is a pass-through. If the cache is warm, great. If not, you are paying the full round-trip penalty back to your origin — and for a blog post that changes once a week, that penalty is pure waste.

When you move the application itself to the edge, you eliminate that entire class of latency. There is no origin to reach back to. The Fastly Compute platform runs your code at the edge in a WebAssembly sandbox, and Fastly's KV Store replicates your data globally. A cache miss does not mean a cross-continent round trip — it means a local KV read and a template render, all within the same POP.

The fastest request is the one that never leaves the edge. When your data, your logic, and your cache are all co-located at the point of presence nearest the reader, latency becomes a function of the speed of light across a datacenter floor — not across an ocean.

The numbers bear this out. Time to first byte for a typical CMS on a cache miss sits around 200–800ms depending on origin location and database load. Edge CMS serves the same content in 10–15ms on a cache miss because the KV Store read and template render happen locally. On a cache hit, you are looking at single-digit milliseconds.

The Data Model

Fastly's KV Store is a globally distributed key-value store. It is not a relational database — there are no joins, no indexes, no query language. You get keys and values, and you design around that constraint.

Edge CMS uses a denormalized index pattern. Each post is stored at its own key with its full content:

  • post:building-a-cms-at-the-edge — the complete post object including markdown content
  • post:kv-store-patterns — another post, independently readable
  • _index — a pre-computed listing of all published posts with metadata
  • _sidebar — the sidebar configuration (categories, links, ordering)

The index key is the important part. Instead of scanning all post keys to build a listing page, we maintain a single denormalized index that contains enough metadata — title, excerpt, tags, date, featured image — to render the homepage with one KV read. When a post is created, updated, or deleted, the admin write path atomically updates both the individual post and the index.

Reading a Post from KV Store

The Compute application reads a post from KV Store, parses the markdown, and renders it through a Handlebars template. Here is the core of the Rust implementation:

use fastly::{KVStore, Error};
use pulldown_cmark::{Parser, Options, html};

fn render_post(slug: &str) -> Result<String, Error> {
    // Open the KV Store by its linked name
    let store = KVStore::open("content")?
        .expect("KV Store 'content' must be linked");

    // Read the post by its key
    let key = format!("post:{}", slug);
    let entry = store.lookup(&key)?
        .ok_or_else(|| Error::msg("Post not found"))?;

    // Parse the JSON post object
    let post: Post = serde_json::from_str(
        &entry.take_body().into_string()
    )?;

    // Convert markdown to HTML
    let parser = Parser::new_ext(
        &post.content, Options::all()
    );
    let mut html_output = String::new();
    html::push_html(&mut html_output, parser);

    Ok(html_output)
}

That is the entire read path. Open the store, look up the key, parse the JSON, convert the markdown. No database driver, no connection pool, no ORM. The KV Store is a first-class primitive of the Compute runtime — accessing it is as straightforward as reading a local file.

Cache Invalidation with Surrogate Keys

Caching is where edge architecture really earns its keep. Every reader-facing response from Edge CMS carries two cache headers and a set of surrogate keys:

  1. Surrogate-Control: max-age=3600 tells Fastly's edge cache to hold the response for one hour
  2. Cache-Control: max-age=60 tells the browser to hold it for one minute
  3. Surrogate-Key: post-building-a-cms-at-the-edge sidebar tags the response with identifiers for targeted purging

When an admin updates this post, the write handler calls the Fastly Purge API with the surrogate key post-building-a-cms-at-the-edge. That single API call invalidates exactly this post's cached response across every Fastly POP worldwide — typically within 150ms. The homepage listing carries the surrogate key post-index, so an index rebuild purges listing pages without touching individual post caches.

This is surgical invalidation. You are not flushing the entire cache. You are not waiting for TTLs to expire. You are telling the CDN precisely which content changed, and it forgets exactly that content and nothing else.

Image Handling with Image Optimizer

Images are stored as binary blobs in Fastly's Object Store, keyed by post slug and filename. When an admin uploads an image through the editor, the Compute application writes it directly to the Object Store.

The real power comes from Fastly Image Optimizer. When a reader's browser requests an image, you do not need to have pre-generated every size and format variant. Instead, you serve the original and let Image Optimizer transform it on the fly via query parameters:

  • ?width=800 — resize to 800px wide, maintaining aspect ratio
  • ?format=webp — transcode to WebP for browsers that support it
  • ?quality=80 — balance between file size and visual fidelity
  • ?crop=16:9 — crop to a specific aspect ratio for consistent layouts

The transformed image is cached at the edge, so subsequent requests for the same dimensions hit the cache. You upload once, and Image Optimizer handles the entire responsive image pipeline without a build step, a Lambda function, or a separate image CDN.

What This Proves

Edge CMS is deliberately a simple application — it is a blog, not an enterprise CMS. The point is not to replace WordPress. The point is to demonstrate that the building blocks for real applications already exist at the edge: compute, storage, caching, image processing, security. These are not toys or limited-use features. They compose into something you would actually deploy.

The entire project is open source, implemented in three languages — Rust, TypeScript, and Go — using identical shared templates. Pick the language you already know, deploy it to your own Fastly account, and you have a working blog running entirely at the edge in under five minutes. No origin infrastructure to provision. No database to manage. No servers to patch at 2am when the next RCE drops.

That is the promise of edge computing, made concrete.
